JRDBは20種類以上の固定長データ形式(SED/KYI/TYB/CYB/OZ/JO/UKC…)を出している。
形式ごとに手でフィールド定義を書くのは非現実的かつ必ず間違える
（TYBで騎手名12バイト=全角6文字によるズレを実際に踏んだ）。
→ **仕様書テキストをパースしてレイアウトを自動生成する設計**にした。

## 4つのスクリプト
| ファイル | 役割 |
|---|---|
| `scripts/jrdb_fetch.py` | **少量・欠落補充専用**（大量取得は安全弁で拒否） |
| `scripts/jrdb_spec.py` | 仕様書.txt → 項目名/バイト位置/型 を自動抽出 |
| `scripts/jrdb_read.py` | 仕様書からレイアウトを作り**任意の形式**を読む汎用リーダー |
| `scripts/jrdb_tyb.py` | TYB専用（先に手書きしたもの。jrdb_readで代替可） |

## 配布URLの構造（実調査で判明）
```
Zip : https://jrdb.com/member/datazip/{Fld}/{YYYY}/{CODE}{YYMMDD}.zip
Lzh : https://jrdb.com/member/data/{Fld}/{CODE}{YYMMDD}.lzh
{Fld} = 種別コードの頭大文字+以降小文字（SED→Sed / TYB→Tyb）
```
クエリパラメータを使わず日付と種別をパスに埋め込む設計。**Zipを優先**
（lzhはPython標準で解凍できない）。

**開催日はjravan.dbから引く**（`jyo<='10'`でJRA10場に限定）。
地方を含めると2025年が362日になり404を大量に叩く。JRA限定で**109日**＝
手持ちのTYB_2025.zipの中身と完全一致し、URL構成の正しさが裏取りできた。

認証は環境変数 `JRDB_USER`/`JRDB_PASS` か `data/jrdb/.credentials`（gitignore済）。

## ⚠️ 規約: 一括取得はしない（実確認済 2026-08）
https://jrdb.com/terms を確認した結果:
- **第8条11項「JRDBの業務を妨げるような行為」を禁止** → 機械的な一括取得は抵触のおそれ
- **レース当日 08:00〜19:00 は過去データDLを制限**（サーバ負荷対策と明記）
- 第5条: 個人利用限定。複製・頒布・公開・第三者提供は一切禁止
- robots.txt は存在しない（404）
「大量取得が許可されている」根拠は**無い**。

→ **過去データは必ず公式の「バックナンバー」（年1ファイル）を使う。**
  16年分でも16リクエスト。日別に109ファイル叩く理由は無い。

jrdb_fetch.py には安全弁を実装済み:
1. 対象が `--max-files`(既定8) を超えたら**実行を拒否**してバックナンバーへ誘導
2. **開催日の08:00〜19:00は実行を拒否**（規約の制限時間帯に合わせる）
3. 1リクエスト3秒待ち・並列化なし
※dry-runは取得しないので時間帯制限の対象外。

検証: TYBで35項目・レコード長128を手書き定義と**完全一致**で抽出できた。

## 調査も自動化できる
```bash
python scripts/jrdb_spec.py               # 全仕様の一覧
python scripts/jrdb_spec.py --grep 不利    # 全仕様を横断して項目名/備考を検索
python scripts/jrdb_spec.py --show sed     # 特定仕様の全項目
python scripts/jrdb_read.py SED            # 読み込んで充足率つき要約
```
**仕様書さえ集めれば「何が取れるか」の調査が手作業ゼロで終わる。**
本体データは必要と分かったものだけ落とせばよい（手順=data/jrdb/SPEC_DOWNLOAD.md）。

## 落とし穴（両方とも実際に踏んだ）
1. **バイト位置はバイト単位**。cp932でデコードしてから文字位置で切ると
   全角を含む項目以降が全部ズレる。必ずバイト列のまま切ってからデコード。
2. `jrdb_spec` / `jrdb_tyb` はインポート時に sys.stdout を差し替える。
   呼び出し側で再度 TextIOWrapper で包むと元が閉じられて以降書けなくなる。

| 項目 | 発火率 | 値 |

「レース中の不利」に期待していたが、**中不利は7日で1頭しか付かない**。
[[reference_jrdb_potential]]で「最有望」としたが、**発火率から見て検出力が厳しい**。
+2ppを検出するのに発火率1.5%だと約34,000頭＝**9ヶ月分**必要
([[verified_roi_claim_credibility]]の計算)。出遅(17.1%)なら現実的。
→ **狙うなら「出遅」または「いずれかの不利(21.8%)」**。細分項目は薄すぎる。

### ⚠zipの中身は単一形式ではない（実際に踏んだ）
SEDのzipには `SED*.txt` の他に `SRB*.txt`(成績レースデータ) と `RCA*.csv`(コメント)が同居。
zip内の全.TXTを読むとSRBをSEDのレイアウトで解釈して**12%が化ける**。
→ jrdb_read.load() は**zip内のファイル名もprefixで絞る**よう修正済み。
副産物: SRB(成績レースデータ・レース単位)も同時に手に入る。

### データの遡り
`--index-url` で会員索引を1回だけ読める。SEDは **1999年から日別zip** で存在。
ただし日別なので年単位の一括取得は規約上NG。必要な期間だけ少量ずつ。
