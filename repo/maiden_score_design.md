## 0. 要約（先に）

- Phase 1（表示のみ）は実装済み。本書は Phase 2「合成スコア」の検証・合成ルールを固定する
- 使える変数は実質 **V1（騎手係数）・V2（黄金ライン）・V3（厩舎当コース勝率）の3つだけ**
  - V5 遅デビュー: 2023 前向き再検証で破棄確定（z=−1.57）
  - V6 調教: 後ろ向き検証不可（oikiri 非蓄積・JV training は 2025-06〜の1年窓）→ 除外
  - V7 血統: 却下済み（人気薄×父 |z|<1.7）
- V1–V3 は「全レースで検証済み」だが **新馬戦での単変数残差は未検証**。新馬は市場構造が違う
  （1番人気の勝率 35.0% vs 全体 28.9%）ため、全レースの証拠をそのまま転用しない
- 追加データパイプラインは **不要**（V1–V3 は jravan のみで完結・`before_key` でリーク防止）
- 判定は §4 の単変数ゲート → §5 の合成 holdout の **2 段階、全て事前固定**

## 2. 変数定義（事前固定・これ以外を足さない）

| # | 変数 | 算出（既存関数を使用・新規ロジック禁止） | 3段階化の方針 |
|---|------|------------------------------------------|----------------|
| V1 | 騎手係数 | `jockey_jv.jockey_factor(..., before_key=当該レース)` の `mult` | train 分布の 3 分位で 2/1/0 点 |
| V2 | 黄金ライン | `jockey_trainer_combo(jockey, trainer_code, before_key=…)` の連対率区分（40/30%）＋ `golden_line_mark` 準拠 | 🥇🥇=2 / 🥇=2? → **いいえ**: 区分は検証済みの段付け（40%+=2 / 30-40%=1 / それ以外・不足=0）に固定 |
| V3 | 厩舎当コース勝率 | `trainer_course_winrate(trainer_code, jyo, surface, before_key=…, min_year=3年前)` の `win_rate_shrunk` | train 分布の 3 分位で 2/1/0 点 |

**人気（V4）はスコアに入れない。** 統制変数（ベースライン）としてのみ使う。
人気を加点に含めるとスコアが人気の再表現になり「市場を超える」意味を失うため。

**リーク防止:** 全変数 `before_key=race_key` を必須とし、当該レース「より前」の成績のみで算出する。
`trainer_code` は当該レースの `results.trainer_code`（出馬時点で確定している事実）を使う。

## 4. Step A: 単変数ゲート（合成の前段）

各変数の 3 段階区分ごとに、holdout の人気統制後 複勝残差を計測する。

| 判定 | 閾値（事前固定） |
|------|------------------|
| 採用 | 上位区分の複勝残差 > 0 かつ z ≥ +2.0、かつ区分間で方向が単調 |
| 不採用 | 上記を満たさない変数は合成に入れない |
| 全滅時 | **採用変数が 1 つ以下なら合成を行わず、Phase 1（表示のみ）のまま維持** |

報告は全変数・全区分の残差を出す（採用した変数だけ見せる選択的報告を禁止）。

## 5. Step B: 合成スコア holdout（一度勝負）

| 項目 | 内容 |
|------|------|
| 合成ルール | Step A 通過変数の 3 段階点を **単純合計**（重みなし）。0〜2×N 点 |
| 3 分位閾値 | train 期間の分布で一度だけ決めて凍結 |
| 成功条件 | ① スコア top 区分の複勝残差 **+3pp 以上** かつ bootstrap 95%CI が 0 を跨がない<br>② スコア上位→下位で複勝残差が **単調減少**<br>③ top 区分の単勝 ROI が同人気帯ベースラインを **悪化させない** |
| NO-GO 時 | Maiden Score は凍結し、Phase 1 表示のまま運用続行。再挑戦は変数の追加候補が検証を通ってから |

## 6. データスヌーピング防止（継承＋追加）

- 上位設計 §6.3 を継承（探索は train のみ・holdout は一度だけ）
- **本設計で 2018–2022 を使うのは今回が初見**であること（V5 発見時に同じ holdout を
  「月齢」軸で観測済みだが、V1–V3 の軸では未観測。ただし同一 holdout の多重使用リスクは
  残るため、GO でも前向き収集での再確認を Phase 3 の受入条件にする）
- スコアの見た目上の良さ（UI モック）を理由に閾値を動かさない
